# getdesign.md 기반 디자인 추천

목표: 완성된 프로젝트의 실제 성격에 맞는 getdesign.md 사례를 **최대 두 개** 고르고, 사용자가
분석 화면을 직접 열어 본 뒤 사람의 취향·브랜드 결정을 내릴 수 있게 한다. 추천이 곧 적용 승인은
아니다.

## 1. 추천 근거 만들기

`PLAN.md`, production URL, 현재 `DESIGN.md`, 대표 화면을 읽어 다음만 요약한다.

- 제품·사용자·사용 맥락: 업무 도구, 소비자 서비스, 콘텐츠, 예약, 교육 등
- 1순위 행동과 정보 밀도: 탐색·입력·비교·결제·읽기 중 무엇이 중요한가
- 신뢰·속도·친근함·표현성 같은 시각 목표와 반드시 유지할 브랜드 요소
- 주요 화면 유형과 mobile 우선 여부
- 고정 UI inventory와 접근성·반응형 제약

승인된 `DESIGN.md`가 있으면 그 시스템과 충돌하는 외부 추천을 하지 않는다. 사용자가 명시적으로
새 방향 비교를 요청했을 때만 충돌 지점을 먼저 밝히고 최대 두 안을 제시한다.

## 2. 카탈로그 검색과 선별

getdesign.md의 카탈로그를 프로젝트 목적·밀도·톤으로 검색한다. 카탈로그 검색 URL은
`https://getdesign.md/design-md?q=[URL-encoded query]` 형식이다. 결과에서 실제 분석 페이지를 열어
화면과 설명을 확인한다.

- 제품 목적·정보 밀도·핵심 행동이 비슷한 사례만 후보로 둔다.
- 단순히 유명하거나 색상이 예쁜 사례는 고르지 않는다.
- 실제 분석 페이지 URL을 확보하지 못한 후보는 추천하지 않는다.
- 원본 서비스의 공식 화면 URL도 확인할 수 있을 때만 함께 제공한다. 추측한 URL은 링크로 쓰지 않는다.
- 자산·카피·로고·완성 코드의 복제 또는 특정 브랜드처럼 보이게 만드는 적용은 제외한다.

## 3. 사용자에게 보일 추천 형식

후보는 많아도 두 개이며, 각 후보의 **분석 화면 링크**는 Markdown으로 클릭 가능하게 만든다.

```md
### 추천 A — [사례 이름](https://getdesign.md/[slug]/design-md)

- 화면 보기: [getdesign.md 분석 화면](https://getdesign.md/[slug]/design-md) ·
  [원본 서비스 화면](https://official.example.com/)  <!-- 확인된 경우만 -->
- 맞는 이유: [프로젝트의 사용자·핵심 행동·밀도와 연결]
- 가져올 원칙: [hierarchy, type relationship, spacing rhythm, component rule]
- 적용 범위: [현재의 경로·컴포넌트]
- 적용하지 않을 것: [브랜드 색·로고·카피·이미지·새 기능]
```

두 안의 차이는 한 줄로 비교한다. 예: `A는 업무 도구의 높은 정보 밀도, B는 처음 쓰는 사용자를 위한
낮은 인지 부하에 맞습니다.` 사용자가 링크를 보고 A/B/현재 디자인 유지를 고르기 전에는 코드를 바꾸지
않는다.

## 4. 선택 뒤 반영

선택한 사례에서 일반화할 수 있는 색상 역할, type scale 관계, spacing rhythm, surface·border 강도,
canonical component 규칙만 `DESIGN.md` 초안에 기록한다. 출처로 getdesign.md 분석 URL과 원본 공식 URL
(있는 경우)을 `reference only`로 남긴다. 기존 `DESIGN.md`와 `PLAN.md`의 고정 조건을 우선하고,
functional/visual QA를 통과한 작은 변경만 채택한다.
