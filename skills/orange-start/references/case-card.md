# 업무 자동화 사례 — CASE.md 작성 규칙

프로젝트 루트의 `CASE.md`는 **이 결과물이 어떤 업무를, 어떻게 바꿨는지** 한 장으로 정리한 사례 카드다.
`MEMORY.md`가 중요한 결정·막힘·해결만 남긴다면, `CASE.md`는 **"어떤 일을 대신하게 됐나
(업무 변화)"**를 최종 결과에서 한 번 정리한다. 비슷한 문제를 풀려는 다른 사람이 그대로 참고할 수
있는 공유·교육용 자료다.

기본으로 만들지 않는다. 사용자가 교육용 사례 카드나 `CASE.md`를 명시적으로 요청했을 때 완성
단계에서 **딱 한 번** 만든다. 개발 중 매 작업마다 교육용 설명을 추가하는 대신 검증된 최종 결과를
재료로 쓴다.

## 언제 만드나 — 자동화/업무 대체형만

전 프로젝트에 만들지 않는다. 사용자 요청이 있고, 웹앱·AI 작업 스킬·자동화 중 **어떤 수작업을
대신하는지가 분명할 때만** 만든다.

- **만든다**: 회비·명단 집계, 신청 접수·정리, 데이터 정리·분석, 문서·메일 자동화, 챗봇/FAQ,
  반복 업무 대시보드 — "원래 사람이 손으로 하던 일"이 있는 경우.
- **건너뛴다**: 단순 소개 페이지, 발표용 정적 데모처럼 대체한 수작업이 없는 경우.
- **애매하면** 사용자에게 한 줄로만 묻는다: "이 결과물이 원래 손으로 하던 어떤 일을 대신해주나요?"
  대신하는 일이 없다고 하면 만들지 않는다 — **빈칸을 억지로 채우지 않는다.**

## 핵심 원칙

- **이미 검증한 걸 재료로 쓴다.** `PLAN.md`의 동기·흐름·증거, 선택적으로 남긴 `MEMORY.md`의
  결정·막힘, 실제 결과와 git 기록을 새로 분석하지 말고 한 장으로 추린다.
- **결과가 아니라 변화를 적는다.** "무엇을 만들었다"가 아니라 **전에는 어떻게 했고 → 이제
  어떻게 되는지**, 그리고 **사람이 어디서 개입하는지**를 적는다.
- **다른 사람이 자기 일에 대입할 수 있게.** 우리 프로젝트만의 고유명사에 기대지 말고, 비슷한
  업무를 하는 사람이 "아, 우리도 이렇게 하면 되겠다"고 느끼게 적는다.
- **사람 말로, 한 장으로.** 입문자가 읽어도 이해되게. 길어지면 카드가 아니다 — 한 화면 분량으로
  끝낸다. 전문용어가 나오면 한 줄로 풀어 준다.
- **날짜는 셸로 얻는다.** `date +%Y-%m-%d`.
- **별도 커밋을 만들지 않는다.** 완성 단계가 어차피 하는 커밋에 `CASE.md`를 함께 담는다.

## 템플릿

`MEMORY.md`와 같은 폴더(프로젝트 루트)에 `CASE.md`로 새로 만든다:

```markdown
# 🍊 업무 자동화 사례 — [결과물 이름]

> 어떤 업무를, 어떻게 바꿨는지 한 장으로 정리한 사례 카드입니다.
> 비슷한 문제를 풀려는 다른 사람이 그대로 참고할 수 있게 적었습니다.
> 만든 과정의 중요한 결정 기록은 같은 폴더 `MEMORY.md`를 참고하세요.   · 정리: [YYYY-MM-DD]

## 한 줄 요약
[누가 — 어떤 일을 — 무엇으로 바꿨다]
(예: 동아리 총무가, 엑셀로 일일이 대조하던 회비 납부 현황을, 자동 집계 대시보드로 바꿨다.)

## 자동화 전 — 원래 어떻게 했나
- **하던 일**: [사람이 손으로 하던 과정을 단계별로 짧게]
- **불편했던 점**: [시간·실수·반복 등 진짜 고통. 가능하면 "한 번에 30분" 같은 숫자로]

## 무엇을 자동화했나
- **결과물이 대신하는 일**: [이제 자동으로 처리되는 부분]
- **일부러 사람한테 남긴 일**: [자동화 안 한 부분과 그 이유. 없으면 생략]

## 사람이 개입하는 지점 (Human-in-the-Loop)
- [최종 확인·승인·예외 처리 등 사람이 꼭 들어가는 자리 + 왜 거기엔 사람이 필요한지]
  (예: 환불 요청은 자동 반려하지 않고 총무가 직접 확인한 뒤 처리)

## 쓴 도구
| 도구 | 어디에 썼나 |
|------|------------|
| Codex 또는 Claude Code | 기획·구현 |
| [웹앱·스킬·자동화에 실제로 쓴 도구] | [용도] |
| [외부 API 등 추가 도구] | [용도. 없으면 이 줄 생략] |

## 업무 흐름 — 전 → 후
- **전**: [수작업 흐름 한 줄]
- **후**: [바뀐 흐름 한 줄 — 이제 사람은 무엇만 하면 되나]

## 다시 만든다면
- [한 번 더 한다면 다르게 할 점 / 비슷한 일을 하려는 다음 사람에게 줄 팁]
```

## 좋은 카드 vs 빈약한 카드

**빈약함 (이렇게 쓰지 않는다):**

```markdown
## 자동화 전 — 원래 어떻게 했나
- 하던 일: 엑셀로 관리했다.
- 불편했던 점: 불편했다.

## 사람이 개입하는 지점
- 사람이 확인한다.
```

**풍부함 (이렇게 쓴다):**

```markdown
## 자동화 전 — 원래 어떻게 했나
- 하던 일: 매달 회원 20명의 회비를 엑셀에 한 명씩 입력하고, 은행 입금 내역과 눈으로 대조해
  안 낸 사람을 손으로 표시했다.
- 불편했던 점: 한 번 집계에 30분 넘게 걸렸고, 입금자 이름이 동명이인이면 누가 냈는지 헷갈렸다.

## 사람이 개입하는 지점 (Human-in-the-Loop)
- 입금 자동 매칭이 애매한 건(이름 불일치·금액 다름)만 '확인 필요'로 모아 보여주고, 총무가
  눈으로 보고 직접 처리한다. 돈 문제라 자동으로 단정하면 사고가 나기 때문이다.
```

오른쪽처럼, 비슷한 업무를 하는 다른 사람이 **자기 상황에 그대로 대입할 수 있을 만큼** 구체적으로 적는다.
