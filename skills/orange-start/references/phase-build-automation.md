# 자동화 구현

목표: `PLAN.md`의 반복 작업을 안전하게 다시 실행할 수 있는 자동화로 만들고, dry-run·중복 방지·
실패 기록까지 확인한다. 단순 스크립트 한 번 실행을 자동화 완성으로 부르지 않는다.

`delivery_intent`가 `implement_and_release`면 dry-run에서 멈추지 않는다. 외부 쓰기는 기존 승인
게이트를 지키되, 승인된 샘플 live-run과 선택한 트리거 활성화·최근 실행 결과 재조회까지 이어간다.

시작할 때 `verification-loop.md`를 읽는다. `PLAN.md`의 TEST↔REQ 연결과 결과물 인벤토리를
구현 순서와 완료 증거의 기준으로 삼는다.

## 1. 실행 계약 확인

다음 항목이 채워져야 구현을 시작한다.

- 트리거: 수동, 일정, webhook, 외부 이벤트
- 실행 위치: 로컬, GitHub Actions, Vercel/서버리스, 기존 업무 도구
- 연결 서비스와 사용할 계정·조직
- 입력→변환→출력 필드 매핑
- 사람이 승인해야 하는 외부 변경
- dry-run 동작
- 중복 방지 기준과 재실행 정책
- 재시도할 오류, 최대 횟수, 영구 실패 처리
- 실행 로그와 실패 알림
- 중지·복구·수동 재실행 방법

모호한 도구 선택은 가장 단순하게 고른다.

| 상황 | 기본 선택 |
|---|---|
| 사람이 필요할 때 실행 | CLI + `--dry-run` |
| 정해진 시각의 짧은 작업 | GitHub Actions `workflow_dispatch` + `schedule` |
| 외부 이벤트 수신 | 서명 검증이 있는 serverless webhook |
| 브라우저 로그인에만 의존하고 안정적 API가 없음 | 완전 자동화를 약속하지 말고 사람 확인 단계 포함 |

노코드 도구는 기획서가 명시적으로 추천하고 코드 자동화로 해결하기 어려운 이유가 있을 때만 쓴다.

구현 전에 결과물 인벤토리에서 트리거, 실행 코드·workflow, 입력→출력 매핑, runbook, 로그·결과의
예상 목록과 수량을 다시 센다. 연결된 TEST의 `준비`, `행동`, `기대 결과`, `통과 증거`를 어느
dry-run·live-run·재조회로 증명할지 표시한다.

## 2. 최소 구조

언어와 프레임워크는 기존 프로젝트와 연결 SDK를 고려해 하나만 고른다.

```text
src/ 또는 scripts/       실행 코드
tests/fixtures/          비식별 샘플 입력
tests/                   변환·중복·오류 테스트
.env.example             변수 이름과 설명, 실제 값 없음
.github/workflows/       GitHub Actions를 선택한 경우만
README.md                실행·중지·복구 runbook
```

처리 로직과 외부 I/O를 분리해 dry-run과 fixture 테스트가 실제 코드 경로를 사용하게 한다.

## 3. 필수 안전장치

### Dry-run

- 기본 실행은 가능한 한 읽기 전용 dry-run으로 둔다.
- `--dry-run`은 예정된 생성·수정·발송 건수와 대상 식별자를 보여주되 민감정보 본문은 출력하지 않는다.
- dry-run과 live-run이 별도 구현으로 갈라지지 않게 같은 처리 계획을 사용한다.

### 중복 방지

- 입력의 안정적인 ID나 내용 hash를 idempotency key로 쓴다.
- 같은 입력을 두 번 넣는 테스트에서 두 번째 실행이 새 결과를 만들지 않아야 한다.
- 체크포인트를 언제 저장하고 실패 후 어디서 재개하는지 명시한다.

### 재시도와 실패

- timeout, rate limit, 일시적 5xx만 제한된 횟수로 backoff 재시도한다.
- 인증 실패, 권한 없음, 유효성 오류는 무한 재시도하지 않는다.
- 부분 성공이면 성공 항목과 실패 항목을 분리해 기록하고 안전하게 재실행할 방법을 제공한다.

### 로그와 비밀값

- run id, 시작·종료 시각, 읽음·성공·건너뜀·실패 건수, 실패 종류를 구조화해 남긴다.
- 토큰·메일 본문·개인정보 전체를 로그에 남기지 않는다.
- 비밀값은 환경변수나 호스팅 secret store에 두고 `.env`, 토큰 파일을 commit하지 않는다.

## 4. 계정·권한 연결

연결 전에 `browser-steps.md`로 실제 로그인 계정과 조직을 확인한다. Google 계정이 여러 개면
사용자가 대상 계정을 선택한 뒤 OAuth를 승인한다. `최근 프로젝트`, 첫 번째 조직, 브라우저 기본
계정을 자동 선택하지 않는다.

필요한 최소 scope만 요청한다. 쓰기·발송·삭제가 있다면 dry-run 뒤 첫 live-run 직전에 사용자에게
대상과 건수를 보여주고 승인받는다. 이 승인은 일반적인 구현 요청과 별개다.

## 5. 트리거 구현

### 일정/GitHub Actions

- 먼저 `workflow_dispatch`로 수동 검증한 뒤 schedule을 켠다.
- cron이 UTC임을 README에 적고 사용자의 시간대로 환산한 값을 확인한다.
- workflow에는 timeout, concurrency 또는 중복 실행 방지, 최소 permissions를 둔다.
- 저장소 visibility가 `PLAN.md`의 공개 범위와 일치하는지 다시 확인한다.

### Webhook

- 서명·timestamp를 검증하고 replay를 막는다.
- 빠르게 응답하고 긴 작업은 안전한 비동기 실행이나 제한된 후속 처리로 넘긴다.
- 잘못된 payload와 중복 이벤트를 테스트한다.

### 로컬 수동 실행

- 실행 명령, 필요한 변수, dry-run, 중지 방법을 README 첫 부분에 둔다.
- 경로·사용자 홈·특정 OS 값을 하드코딩하지 않는다.

## 6. 검증 순서

각 자동화 가능한 행동은 가능한 가장 작은 테스트를 먼저 추가해 의도한 이유로 실패하는 **RED**를
확인하고, 최소 구현으로 **GREEN**을 만든 뒤, 중복과 불필요한 의존성을 줄이는 **REFACTOR** 후 같은
검증을 다시 실행한다. 이어서 다음 경계를 순서대로 확인한다.

1. 비식별 fixture 1건으로 단위·통합 테스트
2. dry-run으로 사용자·이벤트 트리거 → 입력 읽기 → 처리 계획 → 예정 출력·건수까지 확인
3. 같은 입력을 두 번 넣어 중복 결과가 없고 건너뜀 건수가 기록되는지 확인
4. timeout/rate limit 또는 모의 실패로 제한 재시도와 실패 로그 확인
5. 외부 쓰기가 있다면 사용자 승인 후 실제 샘플 **1건만** 실행
6. run id를 기준으로 결과 서비스에서 생성·변경 결과를 다시 읽어 사용자에게 보이는 결과 확인
7. 트리거를 켠 뒤 최근 실행 로그와 다음 실행 조건 확인

실제 외부 변경 승인을 받지 못해 5번을 못 했다면 `DRY_RUN_PASS`이지 `PASS`가 아니다. 완성이라고
과장하지 않고 남은 live 검증을 표시한다. 증거마다 `TESTED | PARTIAL | INFERRED` 등급을 붙이고,
필수 TEST는 실제 트리거부터 결과 재조회까지 기대 결과를 관찰한 `TESTED`일 때만 PASS다.

검증 뒤 결과물 인벤토리의 예상 트리거·파일·매핑·runbook·로그 수량과 실제 수량을 대조한다.
REQ와 연결된 예상 결과물 경로에서만 placeholder, 빈 handler, 고정 성공값, no-op을 점검하고,
저장소 전체의 무관한 TODO나 예제까지 blocker로 넓히지 않는다.

## 7. 첫 작동 결과와 저장

dry-run의 run id와 요약을 사용자에게 먼저 보여준다. 이것이 자동화 유형의 `첫 작동 결과`다.
`PLAN.md` 진행 상황의 `첫 작동 결과`를 체크한다. 그 후 승인된 경우에만 샘플 1건 live-run으로
넘어간다.

`PLAN.md` 검증 증거에 명령·run id·관찰 결과를 기록하고 코드·테스트·체크 상태를 같은 커밋에 담는다.
이번 자동화 구현에서 바꾼 정확한 경로만 `git add --`로 stage하고 cached 목록을 확인한다.

```bash
git commit -m "구현: 자동화 워크플로"
git push
```

모든 REQ 구현이 끝나면 `전체 요구사항 구현`을 체크하고 `phase-verify.md`로 이어간다.
