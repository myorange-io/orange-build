# Stitch 시각 보정 — 첫 배포 뒤 선택적으로

목표: 이미 작동하는 웹앱의 **시각 방향만** 짧게 보정한다. Stitch에서 기능·페이지·데이터를 다시
기획하지 않는다.

## 적용 조건

- `web_app`에만 적용한다.
- 기본값은 건너뛰기다.
- 첫 완결 흐름의 프로덕션 URL이 이미 있어야 한다.
- 발표·랜딩처럼 시각성이 성공 기준의 핵심이거나 사용자가 원할 때만 실행한다.
- 10분, 대표 화면 1개, 수정 요청 1회가 기본 상한이다. 서로 다른 화면 유형이 꼭 필요해도 3개를
  넘기지 않는다.

## 1. 대표 화면과 고정 요소

라이브 URL에서 가장 중요한 화면 하나를 고른다. `PLAN.md`에서 다음을 복사해 **고정 목록**으로
만든다.

- 반드시 남아야 하는 제목·입력·버튼·표·상태
- 가장 중요한 행동
- 추가·삭제할 수 없는 기능과 데이터

Stitch 프롬프트는 다음 제약으로 시작한다.

```text
Visual redesign only. Do not add or remove screens, fields, actions, data,
navigation, or features. Preserve the exact UI inventory and Korean labels below.
Focus only on hierarchy, spacing, typography, color, and responsive layout.
```

이어서 대표 화면의 실제 UI 목록과 원하는 시각 방향을 넣는다. `modern`, `clean` 같은 형용사만
쓰지 말고 강조색·배경·밀도·참고 서비스의 어느 부분을 참고할지 구체적으로 적는다.

## 2. Google 계정 확인

Stitch를 열기 전에 `browser-steps.md`의 Google 다계정 확인 절차를 따른다. 계정 선택 화면에 여러
계정이 있으면 사용자가 프로젝트에 쓸 계정을 직접 고른다. 기본 계정이나 최근 사용 계정을 추측하지
않는다.

이 짧은 디자인 단계는 교육 참가자가 직접 수행한다. 에이전트는 프롬프트와 고정 목록을 제공하고,
참가자는 생성·변형 1회 후 결과를 가져온다.

## 3. 가져오기

스크린샷만 있어도 시각 토큰·위계를 참고할 수 있다. HTML zip이 있으면 더 정확히 읽되, zip이
없다는 이유로 전체 구현을 멈추지 않는다.

산출물에서 다음만 추출한다.

- 강조색·배경·글자·테두리
- 폰트 크기와 굵기 위계
- 주요 영역의 간격·폭·배치
- 공통 버튼·입력·카드 모양

Stitch에서 생긴 새 기능·문구·페이지는 무시한다. `PLAN.md` 화면이 Stitch에 없어도 삭제하거나
다음 버전으로 보내지 않는다. 대표 화면에서 얻은 디자인 시스템으로 나머지 화면을 구현한다.

## 4. 코드 반영과 재배포

하드코딩된 Stitch 마크업 전체를 복사하지 않는다. 기존 컴포넌트와 디자인 토큰으로 시각 값만
반영한다. 고정 목록의 요소·동작·라벨이 그대로인지 비교한다.

production build와 관련 테스트를 실행하고 push한 뒤 같은 프로덕션 URL에서 다시 확인한다.
전후 차이와 유지한 기능 목록을 `MEMORY.md`에 짧게 기록한다.

Stitch 결과가 기존보다 낫지 않으면 사용하지 않고 기본 디자인으로 돌아간다. 더 많은 변형을 위해
구현을 멈추지 않는다.
