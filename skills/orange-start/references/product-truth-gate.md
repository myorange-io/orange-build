# 제품 사실 확인 게이트 — 예시를 실제 규칙으로 만들지 않기

목표: 기획서의 예시·placeholder·추정치를 실제 사업 규칙이나 사용자 대상 사실처럼 구현하지 않는다.
확실하지 않은 핵심 사실은 사람에게 한 번 확인하되, 질문만 던지지 않고 가장 안전하고 제품 가치가
높은 권장안과 대안의 영향을 함께 제시한다.

## 1. 게이트를 적용할 사실

다음 값이 계산, 화면 문구, AI 출력, 자동화 동작 또는 공개 여부에 영향을 주면 확인한다.

- 금액, 가격, 비율, 수수료, 세율, 매칭 공식, 한도, 정산·환불 규칙
- 인원·횟수·성과·사회적 효과 같은 정량 주장과 그 산식
- 신청 자격, 대상, 마감일, 정책, 약관, 법률·의료·안전 관련 주장
- 개인정보 수집·보관·공개 범위, 역할·권한, 승인 주체
- 실제 조직명·연락처·공식 URL·계정·workspace·production 대상
- 자동화가 읽고 쓰는 대상, 발송 조건, 중복 기준, 삭제·갱신 규칙

색상·간격·변수명처럼 사용자에게 사실로 제시되지 않고 쉽게 되돌릴 수 있는 구현 선택에는 이 게이트를
적용하지 않는다.

## 2. 불확실성 신호

아래 중 하나면 확정 규칙으로 해석하지 않는다.

- `예:`, `예시`, `약`, `대략`, `00`, `미정`, `가정`, `임시`, `운영자 확인` 같은 표현
- TEST 한 건의 입력·출력만 있고 일반 공식이나 적용 범위가 없음
- 원본의 두 값이 충돌하거나 본문·표·화면 자료가 서로 다름
- 출처, 기준일, 승인 주체가 없고 최근 변경 가능성이 있는 사실
- 기존 코드의 상수는 있지만 실제 운영 규칙이라는 근거가 없음

특히 `10,000원 → 예: 20,000원`은 그 한 사례의 기대값일 뿐, 별도 근거 없이 `항상 1:1` 공식으로
일반화할 수 없다.

## 3. 판정 순서

1. `SOURCE_PLAN.md`, 사용자가 제공한 공식 자료, 현재 프로젝트의 승인된 설정에서 명시적 규칙을 한 번
   찾는다. 단순 예시와 실제 규칙을 구분한다.
2. 명시적이고 서로 일치하는 근거가 있으면 `FACT_CONFIRMED: source`로 구현한다.
3. 사용자가 이전 대화에서 직접 확정한 값이면 `FACT_CONFIRMED: user`로 구현하고 다시 묻지 않는다.
4. 그래도 불명확하고 위 게이트 대상이면 `FACT_UNVERIFIED`다. 합리적 기본값이나 업계 관행으로 채우지
   말고 사용자에게 한 번 질문한다.
5. 답을 기다리는 동안 그 사실과 무관한 구조·테스트·읽기 전용 작업은 계속한다. 해당 사실을 사용하는
   계산·공개 문구·외부 쓰기·production 릴리스만 `BLOCKED`로 둔다.

웹 검색이나 비공식 자료로 조직의 내부 규칙을 추정하지 않는다. 공개 정책처럼 공식 최신 출처로
확인할 수 있는 사실은 공식 출처를 확인할 수 있지만, 조직별 비율·효과·승인 규칙은 사람의 답이
우선이다.

## 4. 질문할 때 권장안을 함께 제시

한 번에 사실 하나만 다음 형식으로 묻는다. 권장안은 가장 안전하기만 한 축소안이 아니라, 원본 목적을
가장 많이 유지하면서도 거짓 주장을 만들지 않는 선택으로 고른다.

```text
확인이 필요한 값: [결정해야 하는 실제 규칙]
현재 근거: [원본의 짧은 문구와 왜 확정할 수 없는지]
권장안: [추천 선택] — [사용자 신뢰·기능·배포 관점의 이유]
다른 선택:
- [대안 A] — [기능·일정·위험에 미치는 영향]
- [대안 B] — [기능·일정·위험에 미치는 영향]
지금 필요한 답: [한 문장 또는 값 하나]
```

일반적인 권장 우선순위는 다음과 같다.

| 불확실한 사실 | 기본 권장안 |
|---|---|
| 금액·비율·공식 | 실제 값을 확인한다. 계산이 핵심이면 공개 배포를 보류하고, 부가 기능이면 수치 계산만 빼고 나머지를 완성한다. |
| 정량 효과·성과 | 승인된 산식이 없으면 숫자를 제거하고 검증된 정성 문구만 사용한다. |
| 자격·정책·마감 | 확정 전 신청 가능하다고 단정하지 않고 공식 안내 경로 또는 비활성 CTA를 사용한다. |
| 개인정보·권한 | 더 적게 수집하고 더 좁은 권한을 권장하며, 확정 전 production 쓰기를 하지 않는다. |
| 자동화 대상·발송 규칙 | dry-run까지만 구현하고 계정·대상·트리거를 확인한 뒤 live로 전환한다. |
| AI 출력의 외부 사실 | 확인된 출처만 사용하고, 출처가 없으면 모른다고 표시하거나 사용자 자료를 요청한다. |

사용자가 명시적으로 내부 데모나 비공개 프로토타입을 선택하면 예시 데이터를 쓸 수 있다. 이 경우에도
실제 조직 규칙처럼 표현하지 않고 데모 환경 전체에 제품 친화적인 `예시 데이터` 표기를 사용한다.
`TEST-01`, `REQ-02`, `임시 가정`, `운영자 확인 후 변경` 같은 개발 내부 문구를 사용자 화면에 넣지
않는다.

## 5. 면책 문구로 우회하지 않기

확인되지 않은 사실을 먼저 크게 표시하고 하단에 작은 면책 문구를 붙이는 것은 통과가 아니다.
`1:1 매칭 적용`과 `실제 비율은 운영자 확인 필요`를 동시에 보여주는 식으로 불확실성을 사용자에게
떠넘기지 않는다. 내부 불확실성은 `PLAN.md`의 관련 REQ에 `BLOCKED · FACT_UNVERIFIED`로 한 줄 남기고,
공개 UI·AI 최종 출력·외부 메시지에는 승인된 제품 사실만 넣는다.

## 6. 구현과 검증

사용자 답을 받으면 관련 REQ의 `가정과 결정` 또는 상태·증거 칸에 값과 근거를 한 줄로 남긴다. 같은
질문을 반복하지 않고 계산 상수·문구·fixture·TEST 기대값을 함께 수정한다.

기술 테스트와 사실 검증을 구분한다.

- `10,000 → 20,000` 테스트 통과: 코드가 정해진 계산을 수행한다는 증거
- `1:1이 실제 캠페인 규칙임` 확인: 계산에 사용할 사업 사실의 증거

둘 다 있어야 사용자 대상 계산·주장을 `TESTED`로 PASS 처리할 수 있다. 사실 근거가 없으면 코드
테스트가 통과해도 `PARTIAL` 또는 `BLOCKED`다. 최종 검증에서는 사용자에게 보이는 숫자·정책·효과·
자격·권한 주장을 다시 찾아 `FACT_CONFIRMED` 근거와 대조한다.
