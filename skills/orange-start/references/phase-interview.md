# 기획서 작성 — 최신 IA 인터뷰

목표: 기획서가 없거나 구형 문서만 있을 때 Orange Build App과 같은 7개 phase, 최대 10개 질문으로
현재 IA 기획서를 만들고 `phase-plan.md`로 이어간다.

동기화 기준: `myorange-io/orange-build-app` commit
`7378c12104d777b74cb1bc2411bb7b8d3fdfab2f`. 앱 저장소는 읽기 기준일 뿐 수정하지 않는다.

## 목차

1. 진입과 구형 자료
2. 질문 규칙
3. 7개 phase
4. 결과물별 질문
5. 자료 분석
6. SOURCE_PLAN.md 작성

## 1. 진입과 구형 자료

완성된 최신 App 복사문이나 구현 자료 묶음이 없을 때 이 단계를 사용한다.

- 사용자가 아이디어를 한두 문장으로 말했으면 그것을 초기 아이디어로 쓴다.
- 구형 v1·초기 v2 문서가 있으면 대상·문제·흐름·자료 같은 사실만 초기 아이디어로 읽는다. 그 문서의
  결과물 표시 문자열, TEST, 구현 순서를 현재 계약으로 해석하지 않는다.
- 아이디어가 전혀 없으면 먼저 한 번만 묻는다.

  > 무엇을 만들고 싶나요? 지금 떠오른 아이디어를 한두 문장으로 알려주세요.

첫 아이디어 요청과 아이디어 제안은 아래 최대 10개 질문 수에 포함하지 않는다.

### 아이디어 제안 모드

사용자가 아이디어가 없다고 하거나 제안을 요청한 경우에만 사용한다.

- 역할·반복 업무·사용 순간을 근거로 첫 사용자, 문제, 입력, 확인 가능한 결과, 추천 결과물 유형이
  포함된 제안을 한 번에 하나만 보여준다.
- 서로 다른 제안 6개를 준비한다. 결과물 유형이 미정이면 `web_app`, `ai_skill`, `automation`을 두 개씩
  섞고 같은 아이디어를 제목만 바꿔 반복하지 않는다.
- 사용자가 고치거나 선택한 제안을 초기 아이디어로 삼는다. 비밀값·개인정보·고객 원문은 제안에
  재사용하지 않는다.
- `전부 건너뛰기`를 선택하면 현재 제안을 아이디어로 채택하고 확인되지 않은 내용은 가정으로 남긴다.

## 2. 질문 규칙

- phase는 아래 순서의 **7개**다. 후속 질문을 포함한 최대 기획 질문 수는 **10개**다.
- 한 번에 질문은 **하나만** 한다.
- 초기 아이디어와 답에서 구체적으로 확인된 phase는 `covered`로 두고 다시 묻지 않는다.
- 답이 복합 질문의 일부만 채우면 같은 phase에서 빠진 내용만 짧게 후속 질문한다.
- 매 답변 뒤 이해한 내용을 한 문장으로 요약하고 가장 앞선 미확인 phase로 간다.
- 질문마다 선택지 2~3개를 준다. 가장 적합한 추천안을 첫 번째에 두고 설명을 `추천:`으로 시작한다.
  `기타` 선택지는 만들지 않고 자유 입력도 가능하다고 알린다.
- 구조화 질문 기능이 있으면 사용한다. 없으면 같은 질문·선택지를 일반 대화로 제시하고 답을 기다린다.
  특정 호스트의 질문 도구 이름을 필수로 요구하지 않는다.
- 업무 목적, 완료 수준, 필수 자료 의미처럼 구현 방향을 바꾸는 내용은 질문 수를 줄이려고 추측하지
  않는다.
- 모든 phase가 covered이거나 10문항에 도달하면 지금까지의 답과 명시한 가정으로 기획서를 만든다.
- 사용자가 `전부 건너뛰기`, `지금 정보로 만들어줘`라고 하면 더 묻지 않는다.
  `interview_completion: skip_all`을 남기고 모르는 사람·계정·자료를 사실처럼 채우지 않는다.

## 3. 7개 phase

| 순서 | phase id | 확인할 내용 | 기본 질문 |
|---:|---|---|---|
| 1 | `target_problem` | 첫 사용자와 실제 사용 순간 | 이 결과물을 가장 먼저 쓸 사람은 누구이고, 언제 어떤 상황에서 사용하게 될까요? |
| 2 | `blocked_moment` | 현재 방식과 가장 큰 시간·누락·반복 비용 | 이 일은 지금 어떻게 처리하고 있고, 그중 시간·누락·반복이 가장 큰 부분은 무엇인가요? |
| 3 | `solution_flow` | 입력부터 검토 가능한 결과까지 | 사용자가 무엇을 넣으면, 이 서비스가 어떤 결과를 만들어 주면 좋을까요? |
| 4 | `data_privacy` | 반드시 반영할 자료와 실행 환경 | 구현에 반드시 반영해야 할 기존 자료가 있나요? 있다면 자료의 용도와 분석한 내용이 맞는지 확인해 주세요. |
| 5 | `mvp_scope` | 결과물 유형과 첫 구현 포함·제외 | 첫 번째 결과물은 어떤 형태로 만드는 것이 가장 적합할까요? |
| 6 | `ai_human_review` | AI 처리와 사람 승인 경계 | 어디까지 자동으로 처리하고, 사람은 무엇을 반드시 확인하거나 승인해야 할까요? |
| 7 | `success_failure` | 완료 수준과 성공·실패 증거 | 로컬 실행, 다른 사람과 공유, 실제 업무 사용 중 어디까지 완성하면 성공인가요? 어떤 오류나 누락이 남으면 실패인지도 알려주세요. |

결과물 유형이 미정이면 `mvp_scope`에서 다음 세 가지를 비교한다. 현재 답에 가장 맞는 유형을 첫
선택지로 옮기고 추천 이유를 붙인다.

1. 웹앱 — 브라우저에서 사람이 입력·조회·공유해야 함
2. AI 작업 스킬 — Codex나 Claude Code에서 사람이 필요할 때 반복 호출함
3. 자동화 워크플로 — 일정·이벤트·수동 트리거로 도구 사이 작업을 반복함

`success_failure`의 선택지는 다음 canonical 값으로 기록한다.

1. 내 컴퓨터에서 완성 → `completion_level: local`
2. 다른 사람과 공유 → `completion_level: shared`
3. 실제 업무에서 사용 → `completion_level: real_work`

## 4. 결과물별 질문

### `web_app`

- 어느 화면에서 무엇을 입력하고 어떤 결과를 확인할지 묻는다.
- 자료가 있으면 화면·양식·데이터에 어디까지 반영할지 확인한다.
- 저장 정보, 로그인 역할, 접근 권한, 로딩·빈 상태·오류·성공·모바일 조건을 관련 있을 때 묻는다.
- `shared`는 실제 URL과 대상 접근, `real_work`는 실제 자료·계정과 복구 절차까지 완료 기준에 넣는다.

### `ai_skill`

- 누가 Codex·Claude Code에서 언제 호출할지, 필수 입력과 바로 쓸 출력 형식을 묻는다.
- 긍정 트리거, 비트리거, 빈 입력, 도구 부재 폴백을 확인한다.
- 공용 `SKILL.md`와 필요한 `scripts/`, `references/`, `assets/`만 범위에 넣는다.
- `local`도 현재 호스트 개인 경로 등록과 새 작업 호출까지 완료 기준에 넣는다.

### `automation`

- 트리거, 연결 도구와 정확한 계정·조직, 입력→처리→출력 순서를 묻는다.
- dry-run, 중복 키, 제한 재시도, 구조화 로그, 중지·복구를 확인한다.
- 외부 발송·수정·삭제·활성화 직전의 별도 사람 승인을 명시한다.
- `local`은 dry-run, `shared`는 공유 테스트 환경, `real_work`는 실제 업무 결과까지 구분한다.

## 5. 자료 분석

자료가 있으면 파일별로 먼저 열어 아래를 분석하고 사용자에게 한 번에 하나씩 확인받는다.

- 용도: 반드시 반영할 기준 / 참고 자료 / 입력 데이터 예시 / 결과 검증용 예시
- 자료 설명
- 반드시 반영할 내용
- 그대로 유지할 요소
- 적용 위치
- 열린 질문

`MATERIALS.md`가 있으면 원본 `materials/` 파일과 일치하는지 확인한다. 분석 실패·파일 누락·기획서와
충돌이 있으면 임의로 대체하지 않는다. 필수 규칙, 그대로 유지할 요소, 적용 위치, 열린 질문을
사용자가 확인하거나 바로잡기 전에는 `data_privacy`를 covered로 두지 않는다. 자료가 없다는 명시적
답이 있으면 자료 없이 진행한다.

## 6. SOURCE_PLAN.md 작성

답을 한 페이지 분량으로 압축하되 범위를 줄이거나 확인되지 않은 사실을 꾸미지 않는다. 핵심 기능은
1~3개, 사용 흐름은 3~5개, 가정은 최대 3개로 제한한다.

추가 질문 없이 답에서 정확히 3개 TEST를 만든다. `TEST-01`은 대표 성공, `TEST-02`는 빈 입력 또는
잘못된 입력, `TEST-03`은 결과물 유형의 핵심 예외다. 각 TEST에 준비·행동·기대 결과·통과 증거를 둔다.

`함께 구현할 순서`는 첫 번째 작은 완성 1개와 다음 개선 2~4개다. 각 단계는 사용자가 확인할 변화,
완료 확인, 이번 단계에서 하지 않을 것을 반드시 포함한다.

```markdown
## 기획서 메타데이터
- source: orange-start-interview | orange-start-regenerated
- interview_contract_version: 2
- app_sync_commit: 7378c12104
```

`SOURCE_PLAN.md`가 있으면 같은 원본인지 확인하고, 다르면 사용자 동의 없이 덮어쓰지 않는다. 저장한
뒤 `phase-plan.md`에서 IA 실행 계약으로 바꾼다.
