# 검증 루프 — TEST를 구현과 증거에 연결하기

목표: Orange Build App 기획서의 `TEST-01`~`TEST-03`을 참고 문구가 아니라 구현 계약으로 다룬다.
`SOURCE_PLAN.md` 원문은 바꾸지 않고, `PLAN.md`에서 TEST와 REQ, 결과물, 실제 증거를 서로 연결한다.
실패·누락을 발견한 뒤의 수정과 사람 결정 경계는 `self-improvement-loop.md`를 함께 적용한다.

## 1. TEST 계약 가져오기

현재 Orange Build App의 contract v2 기획서에는 정확히 세 시나리오가 있다.

- `TEST-01`: 대표 성공 흐름
- `TEST-02`: 빈 값 또는 잘못된 값
- `TEST-03`: 결과물 유형에 맞는 예외 흐름

각 TEST의 제목과 `준비`, `행동`, `기대 결과`, `통과 증거`를 원문 그대로 옮긴다. 누락된 필드를
추측으로 채워 현재 앱 형식인 것처럼 만들지 않는다. TEST마다 관련 `REQ-*`를 하나 이상 연결하고,
모든 REQ가 적어도 하나의 TEST 또는 더 작은 보조 검증에 포함되는지 확인한다.

TEST가 없는 초기 v2와 v1/legacy 기획서는 구현 계약으로 지원하지 않는다. 호환 TEST를 파생하지
않고 `phase-interview.md`에서 기존 내용을 초기 아이디어로만 사용해 최신 TEST 세 개와
`함께 구현할 순서`를 새로 만든다.

## 2. 결과물 인벤토리

구현 전에 원본과 REQ에서 사용자가 받을 결과물을 세고 `PLAN.md`에 예상 수량과 목록을 적는다.

| 결과물 유형 | 세어야 할 것 |
|---|---|
| `web_app` | 경로·페이지, 완결 사용자 흐름, 데이터·외부 연동, 역할별 상태 |
| `ai_skill` | SKILL.md, scripts/references/assets의 필수 파일, 약속한 출력, 호출 fixture |
| `automation` | 트리거, 실행 코드·workflow, 입력→출력 매핑, runbook, 실행 결과·로그 |

구현 뒤 같은 기준으로 실제 수량을 다시 세고 예상과 대조한다. 원본이 요구한 결과를 합치거나 빼야
한다면 사용자 결정과 이유를 변경 기록에 남긴다. 전역 TODO 검색 결과를 무조건 blocker로 삼지 않는다.
placeholder, 빈 handler, 고정 성공값, no-op은 **REQ와 연결된 예상 결과물 경로**에서만 점검한다.

## 3. 행동 단위 구현 루프

자동화할 수 있는 행동은 가능한 가장 작은 테스트부터 만든다.

1. **RED** — 기대 행동과 실패 경계를 표현하는 테스트를 추가하고 의도한 이유로 실패하는지 확인한다.
2. **GREEN** — 해당 TEST와 REQ를 만족하는 최소 구현을 하고 테스트가 통과하는지 확인한다.
3. **REFACTOR** — 중복과 불필요한 복잡성을 줄인 뒤 같은 테스트가 계속 통과하는지 확인한다.

UI처럼 자동 테스트만으로 의미를 증명하기 어려운 행동도 테스트를 생략하지 않는다. 계산·변환은 단위,
경계 연결은 통합, 사용자 관찰은 브라우저 또는 실제 호출로 나눠 가장 작은 재현 가능한 증거를 남긴다.

선택한 완료 수준의 결과는 다음 경계를 끝까지 이어 확인한다.

```text
사용자 트리거·화면
→ 실제 입력·요청
→ 처리·데이터 변화·외부 호출
→ 응답·생성 결과
→ 사용자가 보는 결과와 실패 안내
```

웹앱은 로컬 결과 또는 production URL과 console·network·저장 후 재조회, AI 스킬은 새 작업의 실제
입력과 출력, 자동화는 완료 수준에 맞는 dry-run·공유 테스트·실업무 run id와 결과 재조회로 이
경계를 증명한다.

검증 실패, 원본 요구 누락, 실제 결과의 오류는 완료 보고만 하고 멈추지 않는다. 원본 범위 안의
안전한 수정은 AI가 자동으로 적용하고 가장 가까운 검증과 영향을 받는 전체 게이트를 다시 실행한다.
범위·비용·권한·삭제·외부 발송처럼 선택과 책임이 달라질 때만 사람의 결정을 받는다.

### `PLAN.md`는 IA 경계에서만 갱신

RED→GREEN→REFACTOR, 설치, 가까운 재검증을 반복하는 동안에는 `PLAN.md`를 고치지 않는다. 상세
과정은 코드·테스트·CI·실행 로그가 증거다. 아래 경계에서만 관련 행을 한 번에 갱신한다.

1. 최초 계약을 만들 때
2. 현재 STEP이 `AWAITING_APPROVAL → IN_PROGRESS → AWAITING_REVIEW → APPROVED`로 전이할 때
3. 사람 결정으로 범위·비용·권한·공개 범위가 실제 변경됐을 때
4. 외부 blocker나 세션 종료로 다음 사람이 이어야 하는 handoff를 남길 때
5. 최종 검증에서 PASS·FAIL·미검증 상태를 확정할 때

평범한 commit이나 작은 수정 때문에 상태 문서를 수정하지 않는다. 단계 상태 전이에는 구현 위치와
관찰 결과 한 줄만 남긴다. 원본 근거와 완료 조건 문장은 사람의 범위 변경 결정 없이는 다시 쓰지
않는다. 실패 후보, 버린 patch, 중간 명령 출력은 `PLAN.md`에 복사하지 않는다. commit이 계약에
포함되면 문서와 해당 코드·테스트를 함께 저장한다.

### 최종 `MEMORY.md`는 한 번만 기록

모든 IA STEP과 선택한 완료 수준의 게이트가 PASS면 `memory-log.md`에 따라 프로젝트 루트의 `MEMORY.md`를
반드시 생성하고 최종 검증 결과를 기록한다. `<!-- orange-build:final-verification -->` 시작 marker와
종료 marker가 각각 정확히 하나여야 한다. 재검증·재배포에서는 새 항목을 append하지 않고 기존 marker
블록을 갱신한다. 이 완료 기록이 없거나 중복이면 최종 완료 판정은 PASS가 아니다.

## 4. 증거 등급과 상태

각 REQ와 TEST의 실제 증거에 다음 등급 하나를 붙인다.

| 등급 | 의미 | 완료 판정 |
|---|---|---|
| `TESTED` | 계획한 입력과 행동을 실제 실행했고 기대 결과를 관찰함 | PASS 가능 |
| `PARTIAL` | 일부 계층·분기만 실행했거나 대체 검증만 통과함 | PASS 불가 |
| `INFERRED` | 코드·설정·HTTP 상태만 보고 동작을 추론함 | PASS 불가 |

`NOT_RUN`, `FAIL`, `BLOCKED`도 그대로 구분한다. 필수 TEST는 `TESTED` 증거가 있을 때만 PASS다.
외부 권한 때문에 dry-run만 확인한 자동화는 `DRY_RUN_PASS / PARTIAL`이며 live PASS가 아니다.

### 제품 사실 증거

사용자에게 보이는 금액·비율·정량 효과·자격·정책·개인정보·외부 실행 규칙은 동작 증거 외에
`FACT_CONFIRMED: source | user` 근거가 있어야 한다. 단일 TEST의 예시값, 코드 상수, 화면 캡처는
사업 사실의 근거가 아니다. 사실이 `FACT_UNVERIFIED`면 관련 REQ와 TEST는 기술 테스트가 통과해도
`BLOCKED` 또는 `PARTIAL`이며 PASS 수에 포함하지 않는다. `product-truth-gate.md`에 따라 사용자에게
권장안과 대안을 제시하고 확인한다.

## 5. 완료 전 독립 리뷰

기본 판정은 현재 결과물의 계약·결정적 테스트·실제 관찰에 내장한다. 구현과 분리된 사람이나 모델의
독립 리뷰는 반복 회귀, 고위험 외부 변경, 상충하는 증거, 모호한 품질, 두 버전 비교 중 하나가 있을
때만 활성화한다. 조건이 없으면 같은 체크리스트로 최종 self-review를 한 번 수행하고
`independent_review: NOT_NEEDED`와 이유를 적는다.

1. `SOURCE_PLAN.md`와 REQ·TEST의 범위 누락
2. 정상·빈 값·오류·권한·재실행의 정확성
3. 불필요한 복잡성·중복·의존성
4. 비밀값·개인정보·권한·외부 변경의 안전성
5. 증거가 완료 주장을 실제로 뒷받침하는지

판정은 `PASS | FAIL | EVIDENCE_MISSING`으로 기록하고 숫자 점수를 만들지 않는다. 발견 사항은
`P0`~`P3`로 기록한다. P0/P1은 관련 REQ와 TEST를 TODO/FAIL로 다시 열고 구현 단계로
돌아가 자동 수정·재검증한다. P2/P3도 원본 범위 안의 안전한 수정이면 자동으로 해결하고, 중요한
사람 결정이 필요한 항목만 영향과 선택지를 남긴다. 최종 보고에는 TESTED가 아닌 항목을
`아직 증명하지 못한 것`으로 모아 숨기지 않는다.
