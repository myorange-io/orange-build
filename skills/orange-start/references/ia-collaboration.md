# IA 협력 구현 계약

목표: AI가 한 번에 대신 완성하는 흐름이 아니라, 사람이 작은 결과를 확인하고 다음 방향을 선택하며
판단과 실행 능력을 확장하는 IA(Intelligence Augmentation, 지능 증강) 방식으로 구현한다.

## 목차

1. 시작 계약
2. 단계 상태와 전이
3. 사용자 확인 방식
4. 완료 수준
5. 결과물별 완료 게이트
6. 별도 실행 확인
7. 기록과 재개

## 1. 시작 계약

`PLAN.md`에 다음 메타데이터를 반드시 둔다.

```markdown
- workflow: ia_collaborative
- completion_level: local | shared | real_work
- current_step: STEP-NN | complete
```

`completion_level`은 사용자가 인터뷰나 최신 기획서에서 고른 수준이다. 모호하면 추천안을 첫 번째에
둔 선택지 2~3개로 한 번에 하나만 묻는다. 구조화 질문 기능이 있으면 사용하고, 없으면 같은 선택지를
일반 대화로 제시한 뒤 답을 기다린다. 특정 호스트의 질문 도구 이름은 필수 조건으로 삼지 않는다.

원본의 `함께 구현할 순서`를 `STEP-01`부터 순서대로 옮긴다. 첫 단계는 좁은 입력 하나, 검토 가능한
결과 하나, 사람 확인 지점 하나가 이어지는 작은 완성이어야 한다. 기술 기반 작업만으로 단계를 만들지
않는다.

## 2. 단계 상태와 전이

각 단계의 상태는 아래 네 값만 사용한다.

```text
AWAITING_APPROVAL → IN_PROGRESS → AWAITING_REVIEW → APPROVED
```

- `AWAITING_APPROVAL`: 확인할 변화, 완료 확인, 이번 단계에서 하지 않을 것을 보여주고 승인을 기다린다.
- `IN_PROGRESS`: 사용자가 현재 단계를 명시적으로 승인한 뒤에만 들어간다. 이때부터 해당 단계 범위의
  프로젝트 파일을 수정할 수 있다.
- `AWAITING_REVIEW`: 실행 가능한 결과와 검증 증거를 보여주고 사용자의 선택을 기다린다.
- `APPROVED`: 사용자가 `이대로 다음 개선`을 골랐을 때만 기록한다.

`current_step`과 일치하는 단계 하나만 실행할 수 있다. 미래 단계가 표에 있어도 미리 구현하지 않는다.
상태를 추측해서 넘기거나, 계획에 동의했다는 이유로 모든 단계를 승인받은 것으로 해석하지 않는다.

### 단계 시작

다음 형식으로 짧게 보여주고 `이 단계부터 만들까요?`라고 묻는다.

```text
STEP-01 · [단계 이름]
- 확인할 변화: [사용자가 보게 될 변화]
- 완료 확인: [직접 확인할 방법]
- 이번 단계에서 하지 않을 것: [경계]
```

명시적 동의 전에는 코드, 설정, 데이터, 프로젝트 문서를 수정하지 않는다. 읽기 전용 조사와 기존 상태
확인은 가능하지만, `PLAN.md` 상태도 승인 전에 `IN_PROGRESS`로 바꾸지 않는다.

### 단계 구현

승인 후 `IN_PROGRESS`로 전환하고 그 단계만 구현한다. 승인받은 범위 안의 기술 선택, 오류 수정,
테스트는 스스로 진행한다. 범위·비용·권한·공개 범위가 바뀌면 멈추고 다시 확인한다.

### 단계 검토

실행 방법, 주요 변경, 실제 결과, 검증과 남은 확인을 쉬운 한국어로 요약한 뒤 상태를
`AWAITING_REVIEW`로 둔다. 결과는 화면, 파일, 실제 호출 출력, 테스트, run id처럼 사용자가 직접
확인할 수 있어야 한다. 이어서 정확히 다음 선택을 제시하고 답을 기다린다.

1. `이대로 다음 개선`
2. `현재 결과 수정`
3. `구현 방향 다시 정하기`

- `이대로 다음 개선`: 현재 단계를 `APPROVED`로 바꾸고 다음 STEP을 `current_step`으로 지정한 뒤,
  다음 단계의 시작 확인부터 반복한다.
- `현재 결과 수정`: 현재 단계에 머물러 요청을 반영하고 다시 관찰 가능한 결과를 보여준다.
- `구현 방향 다시 정하기`: `SOURCE_PLAN.md`는 보존하고 현재·미래 STEP과 연결 REQ·TEST를 고친 뒤
  현재 단계를 다시 `AWAITING_APPROVAL`로 돌려 승인받는다.

## 3. 사용자 확인 방식

- 한 번에 질문 하나만 한다.
- 선택지는 2~3개만 주고 가장 적합한 추천안을 첫 번째에 둔다.
- 추천안 설명은 `추천:`으로 시작해 이유를 한 문장으로 쓴다.
- 선택지 밖의 자유 입력도 받을 수 있다고 알린다.
- Codex에서는 `$orange-start`, Claude Code에서는 `/orange-start`를 예로 들 수 있지만 자연어
  `오렌지 빌드 시작`도 같은 호출로 인정한다.
- Codex의 지속 규칙은 `AGENTS.md`, Claude Code의 지속 규칙은 `CLAUDE.md`에서 읽는다. Orange Build를
  위해 두 파일을 자동 생성하거나 서로 복제하지 않는다.

## 4. 완료 수준

| 값 | 사용자가 원하는 결과 | 공통 종료 조건 |
|---|---|---|
| `local` | 현재 컴퓨터에서 핵심 흐름 확인 | 외부 공유나 실제 업무 변경 없이 대표 흐름과 실패 경계를 직접 검증 |
| `shared` | 다른 사람이 같은 결과 재현 | 공유 URL·격리 설치·공유 테스트 환경에서 접근과 재현을 검증 |
| `real_work` | 실제 업무에 사용 | 실제 자료·계정·대상 결과, 실패 복구와 되돌리기 절차까지 검증 |

선택한 수준보다 높은 배포·활성화를 완료 조건으로 강요하지 않는다. 반대로 낮은 수준의 증거로 높은
수준을 완료했다고 말하지 않는다.

## 5. 결과물별 완료 게이트

| 결과물 | `local` | `shared` | `real_work` |
|---|---|---|---|
| `web_app` | 로컬 핵심 입력→처리→결과, 관련 오류·빈 상태·권한·모바일 조건 | 실제 공유 URL, 대상 접근, 저장·재조회와 역할별 흐름 | 실제 자료·계정의 업무 결과, 운영 오류와 복구·되돌리기 |
| `ai_skill` | 현재 호스트 개인 스킬 경로 등록 후 새 작업에서 대표 호출 | 격리 또는 대상 환경 설치, 다른 작업에서 같은 호출 결과 | 실제 업무 자료·도구로 결과 생성, 실패 시 안전한 폴백과 복구 |
| `automation` | 외부 변경 없는 dry-run, 중복 방지, 제한 재시도와 로그 | 공유 테스트 환경에서 승인된 샘플 실행과 결과 재조회 | 실제 계정·업무 대상 실행, 중복·실패 복구와 중지 절차 |

AI 스킬 등록 경로는 현재 호스트에 맞춰 고른다.

- Codex: `$CODEX_HOME/skills`, 값이 없으면 `~/.codex/skills`
- Claude Code: `~/.claude/skills`

등록할 때 `SKILL.md`, `scripts/`, `references/`, `assets/` 등 실행에 필요한 파일을 함께 옮긴다. 같은
이름이 있으면 덮어쓰기 전에 알린다. 등록 뒤 반드시 **새 작업**에서 실제 설명과 트리거를 기준으로
대표 요청을 실행한다. Codex의 `$스킬이름`, Claude Code의 `/스킬이름`, 자연어 호출 중 현재 호스트가
지원하는 방법을 사용하며 한 표기만 정답으로 가정하지 않는다.

## 6. 별도 실행 확인

단계 승인과 별개로 다음 작업은 실행 직전에 대상·범위·영향을 보여주고 다시 확인한다.

- 배포와 공개 범위 변경
- 외부 발송·게시·알림
- 실제 데이터 생성·수정·삭제·마이그레이션
- 자동화 트리거 활성화와 실제 계정 live-run
- 결제·비용 발생·권한 확대

이 확인은 해당 STEP 승인으로 갈음하지 않는다. 확인받지 못하면 되돌릴 수 있는 구현과 dry-run까지만
진행하고, 선택한 완료 수준에서 남은 항목을 분명히 표시한다.

## 7. 기록과 재개

`PLAN.md`는 최초 계약, 단계 상태 전이, 중요한 사람 결정, 실제 blocker handoff, 최종 판정에서만
갱신한다. 단계 안의 작은 수정·테스트마다 문서를 고치지 않는다. 상태를 바꿀 때 현재 STEP의 구현
위치와 관찰 증거를 한 줄로 함께 남긴다.

`orange-resume`은 가장 먼저 `workflow`, `completion_level`, `current_step`, 현재 단계 상태를 읽는다.
`AWAITING_APPROVAL`이면 승인 질문부터, `IN_PROGRESS`면 실제 파일·테스트를 대조해 구현부터,
`AWAITING_REVIEW`이면 결과와 세 선택지를 다시 보여주는 것부터 재개한다. `APPROVED`인 마지막 단계만
있으면 다음 STEP 또는 최종 검증으로 간다.

선택한 완료 수준의 모든 REQ·TEST와 단계가 검증된 뒤에만 `memory-log.md`의 marker 블록 하나를
생성하거나 갱신한다. `local` 완료에도 marker를 기록할 수 있지만, 그 안의 결과를 배포·실업무 성공으로
과장하지 않는다.
