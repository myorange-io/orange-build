# 만들기 기록 — MEMORY.md 작성 규칙

프로젝트 루트의 `MEMORY.md`는 구현 완료 증거다. `delivery_intent: implement_and_release`가 모든 필수
REQ·TEST와 결과물별 릴리스 게이트를 통과해 최종 완료 판정을 내릴 때 반드시 생성하고, 최종 검증
결과를 정확히 한 번 기록한다. 사용자의 별도 기록 요청을 기다리지 않는다.

세 스킬(`orange-start` · `orange-resume` · `orange-secure`)과 `orange-design`이 이 한 파일을 공유한다.
설치·작은 수정·개별 테스트·첫 배포마다 쓰는 진행 일지는 아니다.

## 1. 필수 최종 기록 게이트

다음 조건을 모두 충족한 직후, 최종 보고와 commit·push 전에 기록한다.

- `PLAN.md`의 모든 필수 REQ가 PASS다.
- 원본 또는 `derived_compat` TEST가 계획한 증거 수준으로 모두 `TESTED`다.
- P0/P1이 없고 결과물 유형별 production URL·새 컨텍스트 호출·승인된 live-run 증거가 있다.
- `FACT_UNVERIFIED`와 사용자 권한·외부 서비스 blocker가 남아 있지 않다.
- `PLAN.md`의 최종 판정이 실제 증거와 일치한다.

첫 GREEN, dry-run만 통과한 자동화, build만 성공한 웹앱, `PARTIAL`·`INFERRED`가 남은 상태에는
`MEMORY.md`를 완료 기록처럼 만들지 않는다. `plan_only`도 생성 대상이 아니다. 미완료 상태에서 이미
파일이 있더라도 필수 최종 검증 블록을 쓰지 않는다.

## 2. 정확히 한 번 기록하는 방법

필수 최종 기록은 아래 고정 marker 한 쌍으로 식별한다.

```markdown
<!-- orange-build:final-verification -->
[최종 검증 내용]
<!-- /orange-build:final-verification -->
```

- 파일이 없으면 짧은 헤더와 marker 블록을 함께 만든다.
- 파일은 있지만 marker가 없으면 파일 끝에 블록 하나만 추가한다.
- marker 블록이 이미 하나 있으면 새 항목을 append하지 않고 그 블록 안의 결과만 최신 증거로
  교체한다. `orange-resume`, 재검증, 재배포도 이 규칙을 따른다.
- marker가 중복돼 있으면 내용을 잃지 않게 합친 뒤 marker 한 쌍으로 정규화한다. 중복 블록을 더
  추가하지 않는다.
- 최종 완료를 선언하기 전에 시작 marker와 종료 marker가 각각 정확히 한 개인지 확인한다.

이 규칙에서 “한 번”은 최종 검증 항목이 파일에 하나만 존재한다는 뜻이다. 이후 디자인·보안 수정으로
최종 상태가 바뀌면 같은 블록을 갱신할 수 있지만 두 번째 `최종 검증` 항목을 만들지 않는다.

## 3. 파일과 최종 검증 형식

파일이 없으면 다음 최소 형식으로 만든다. 날짜는 `date +%Y-%m-%d`로 확인한다. commit·deployment·
run id는 실제로 관찰한 값만 적고, 아직 만들어지지 않은 최종 commit SHA를 추측하지 않는다.

```markdown
# 🍊 만들기 기록 — [결과물 이름]

## 한눈에 보기
- 무엇을: [PLAN.md 한 줄 소개]
- 결과물 유형: [web_app / ai_skill / automation]
- 결과: [production URL / 대표 스킬 결과 / 자동화 run id]

## 기록

<!-- orange-build:final-verification -->
### [YYYY-MM-DD] 최종 검증
- **최종 판정**: 완료 — REQ [M/M] PASS · TEST [T/T] TESTED
- **확인한 결과**: [사용자가 직접 확인할 수 있는 핵심 결과]
- **검증 근거**: [핵심 검증 최대 3개와 실제 관찰]
- **저장·배포**: [검증한 commit 또는 deployment/run id · GitHub URL · 배포/활성화 상태]
- **아직 증명하지 못한 것**: 없음
<!-- /orange-build:final-verification -->
```

최종 완료라면 `아직 증명하지 못한 것`은 원칙적으로 `없음`이다. 허용된 P2/P3나 사용자가 명시적으로
수용한 제한이 완료 판정과 공존한다면 ID·영향·근거를 짧게 적고 `없음`으로 꾸미지 않는다. 긴 명령,
전체 로그, REQ·TEST 원문은 복사하지 않고 `PLAN.md`와 실제 증거 위치를 요약한다.

## 4. 중간 기록은 선택 사항

사용자가 과정 기록이나 교육 사례를 명시적으로 요청한 경우에만, 다음처럼 나중에 다시 판단할 가치가
있는 사건을 최종 블록 앞에 마일스톤당 최대 한 항목으로 남길 수 있다.

- 다음 구현에도 영향을 주는 제품·기술·디자인·배포 결정
- 반복 blocker의 재현 가능한 원인과 해결
- 사람이 범위·비용·권한·데이터·공개 범위를 바꾼 결정

평범한 package 설치, 파일 생성, 작은 버그 수정, 테스트 통과, commit·push, `PLAN.md` 상태 변경은
중간 기록 조건이 아니다. 같은 사실을 `PLAN.md`, 테스트 출력, git 이력에서 복제하지 않는다. 중간
항목은 append만 하고, 기존 사용자의 기록을 덮어쓰지 않는다.

```markdown
### [YYYY-MM-DD] [중요 결정 / blocker 해결 / 방향 변경]
- **정한 것 / 한 것**: [실제 결정이나 해결]
- **왜**: [이유]
- **막힌 점 / 바꾼 점**: [원인과 재현 가능한 해결]
- **배운 것 / 다음**: [다른 작업에도 적용할 교훈]
```

## 5. 안전·저장 규칙

- 비밀번호·토큰·secret·개인 이메일·고객 원문·불필요한 개인정보를 기록하지 않는다.
- 최종 검증 블록은 `PLAN.md` 최종 판정, 코드·테스트와 같은 최종 커밋에 넣는다. 별도 기록 커밋을
  만들지 않는다.
- 이번 작업의 정확한 파일과 `SOURCE_PLAN.md`, `PLAN.md`, `MEMORY.md`만 필요에 따라 `git add --`로
  stage하고 cached 목록을 확인한다.
- 구현 완료 후 `MEMORY.md`가 없거나 marker가 정확히 하나가 아니면 완료 게이트는 FAIL이다.

## 6. Orange Build App으로 가져갈 때

`SOURCE_PLAN.md`의 `source`가 `orange-build-app`인 작업은 완료 뒤 사용자가 원할 때 이 파일을 App의
만들기 기록으로 가져갈 수 있다. 가져오기는 구현 완료 조건이 아닌 선택 사항이다.

- 업로드 전에 토큰·비밀번호·키와 불필요한 개인정보가 없는지 검사한다.
- App의 256KB 제한을 확인한다. 초과하거나 민감정보가 있으면 몰래 줄이거나 바꿔 올리지 않는다.
- 업로드 직전에 파일 전체가 App에 저장된다는 사실을 설명하고 **명시적 프라이버시 동의**를 받는다.
- 참가자 회고는 에이전트가 꾸며내지 않는다. 사용자가 자신의 말로 직접 쓴 문장만 입력을 보조한다.
- 실제 브라우저 절차는 `browser-steps.md`의 선택적 App 복귀 흐름을 따른다.
