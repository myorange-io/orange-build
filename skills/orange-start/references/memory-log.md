# 만들기 기록 — MEMORY.md 작성 규칙

프로젝트 루트의 `MEMORY.md`는 기본 산출물이 아니다. 사용자가 과정 기록, 교육 사례, App으로 가져갈
만들기 기록을 명시적으로 요청했을 때만 만든다. 요청받은 경우에도 **나중에 다시 판단할 가치가 있는
결정·막힘·해결**만 남기며 일상 진행표로 쓰지 않는다.

세 스킬(orange-start · orange-resume · orange-secure)이 이 한 파일을 공유한다.

## 기록 게이트

사용자 요청이 있고 아래 중 하나가 실제로 생겼을 때만 쓴다.

- 다음 구현에도 영향을 주는 제품·기술·디자인·배포 결정을 내림
- 같은 오류가 반복되거나 진행을 막은 blocker의 원인과 재현 가능한 해결을 찾음
- 버린 선택지나 실패 후보에서 다시 쓸 수 있는 교훈을 얻음
- 사람이 범위·비용·권한·데이터·공개 범위를 결정함
- 최종 검증에서 원본 대비 중요한 방향 변경이나 남은 위험을 확정함

평범한 package 설치, 파일 생성, 작은 버그 수정, 테스트 통과, commit·push, `PLAN.md` 상태 변경은
그 자체로 기록 조건이 아니다. 같은 사실이 `PLAN.md`, 테스트 출력, git 이력에 있으면 복제하지 않는다.
사용자 요청이 없거나 쓸 사건이 없으면 `없음` 항목을 만들지 않고 **`MEMORY.md`를 만들거나 수정하지
않는다.** 중요한 사람 결정과 blocker는 재개에 필요한 최소 내용만 `PLAN.md`의 `가정과 결정`에 둔다.

## 작성 원칙

- **마일스톤당 최대 한 항목** — 같은 완결 흐름에서 생긴 관련 결정·막힘·해결은 하나로 묶는다.
- **짧지만 재사용 가능하게** — 무엇을 결정했는지, 왜, 막힘과 해결, 다음에 적용할 교훈만 3~5개
  bullet로 쓴다. 명령 전체나 긴 로그는 복사하지 않고 필요한 오류·해결 단서만 남긴다.
- **append만 한다** — 기존 항목을 덮어쓰지 않는다. 배포 URL이 처음 생겼을 때 `한눈에 보기`의
  `라이브:`만 갱신할 수 있다.
- **계약을 재작성하지 않는다** — 원본 요구와 REQ·TEST는 `SOURCE_PLAN.md`와 `PLAN.md`에 둔다.
- **사람 말로 쓴다** — 입문자가 이해할 수 있게 쓰고 전문용어는 필요한 경우 한 줄로 푼다.
- **날짜는 셸로 얻는다** — `date +%Y-%m-%d` 결과를 항목 제목에 넣는다.
- **별도 커밋을 만들지 않는다** — 기록 조건을 충족한 마일스톤의 코드·테스트·`PLAN.md`와 함께
  저장한다. 기록 조건이 없으면 stage 목록에 `MEMORY.md`를 넣지 않는다.

## Orange Build App으로 가져갈 때

`SOURCE_PLAN.md`의 `source`가 `orange-build-app`인 작업은 완료 뒤 사용자가 원할 때 이 파일을 App의
만들기 기록으로 가져갈 수 있다. 현재 항목 이름인 `정한 것 / 한 것`, `왜`, `막힌 점 / 바꾼 점`,
`배운 것 / 다음`을 유지해 App이 단계별 기록을 구분할 수 있게 한다.

- 가져오기는 구현 완료 조건이 아닌 선택 사항이다. 업로드를 권하기 전에 파일에 토큰·비밀번호·키,
  이메일·고객 원문 등 불필요한 비밀값이나 개인정보가 없는지 다시 검사한다.
- App의 256KB 제한을 확인한다. 초과하거나 민감정보가 있으면 원본을 몰래 줄이거나 바꿔 올리지
  않고 사용자에게 이유를 알린다.
- 업로드 직전에 파일 범위와 App에 전달된다는 사실을 말하고 **명시적 프라이버시 동의**를 받는다.
  설치·브라우저 제어에 대한 이전 동의를 업로드 동의로 대신하지 않는다.
- App의 참가자 회고는 이 기록을 요약해 에이전트가 대신 작성하지 않는다. 사용자가 자신의 말로
  직접 한 문장 이상 작성하며, 에이전트는 사용자가 이미 작성하거나 말한 문장을 그대로 옮기는
  보조만 할 수 있다.
- 실제 브라우저 이동·URL 연결·업로드 절차는 `browser-steps.md`의 선택적 App 복귀 흐름을 따른다.

## 파일이 없으면 — 사용자가 기록을 요청했을 때만

새 프로젝트라도 자동으로 만들지 않는다. 사용자가 기록을 요청했고 기록 게이트를 통과한 사건이 있을
때만 아래 짧은 헤더와 첫 항목을 만든다.

```markdown
# 🍊 만들기 기록 — [결과물 이름]

> 이 결과물을 어떤 과정으로 만들었는지 남기는 기록입니다.
> 나중에 복기하거나, 다른 사람에게 사례로 보여줄 때 씁니다.

## 한눈에 보기
- 무엇을: [PLAN.md 한 줄 소개]
- 누구를 위해: [주 사용자 / 보여줄 사람 한 명]
- 핵심 흐름: [PLAN.md 핵심 흐름 한 줄 요약]
- 결과물 유형: [web_app / ai_skill / automation]
- 도구: [실제로 선택한 런타임·서비스]
- 시작: [YYYY-MM-DD]   · 라이브: 배포 전

---

## 기록

### [YYYY-MM-DD] 기획
- **정한 것 / 한 것**: [결과물 유형과 핵심 흐름]
- **왜**: [사용자 문제와 이 방향을 고른 이유]
- **고민하다 버린 선택지**: [실제로 비교한 선택지가 있을 때만]
```

이미 `MEMORY.md`가 있으면 헤더를 다시 만들지 않는다. 기록 게이트를 통과한 사건이 있을 때만 아래
형식으로 파일 끝에 덧붙인다.

## 항목(entry) 형식 — 기록할 사건이 있을 때만

마일스톤 하나에 항목 하나만 쓴다. 해당하지 않는 줄은 `없음`으로 채우지 말고 생략한다.

```markdown
### [YYYY-MM-DD] [단계 이름]
- **정한 것 / 한 것**: [이 단계에서 실제로 만들거나 정한 것]
- **왜**: [그 선택의 이유 — 다른 길도 있었는데 왜 이걸로?]
- **어떻게**: [재현에 필요한 핵심 방법·도구]
- **막힌 점 / 바꾼 점**: [무슨 증상이었고, 원인이 뭐였고, 무슨 명령/수정으로 풀었나.
  방향을 바꿨다면 무엇 때문에]
- **배운 것 / 다음**: [다른 작업에도 적용할 교훈 또는 남은 중요 위험]
```

단계 이름은 사건에 맞춰 `기획` · `중요 결정` · `blocker 해결` · `방향 변경` · `최종 검증` ·
`보안 수정`처럼 쓴다. `환경·계정 준비`, `구현`, `이어가기`라는 단계가 끝났다는 이유만으로는 쓰지
않는다.

## 기록하지 않는 예와 기록하는 예

**평범한 진행이라 기록하지 않음:**

```markdown
Node.js package를 설치하고 build가 통과했다. GitHub에 push했다.
```

이 내용은 package·lockfile, 테스트 결과, git 이력으로 충분하다.

**다시 쓸 수 있는 blocker 해결이라 기록함:**

```markdown
### 2026-05-30 blocker 해결
- **정한 것 / 한 것**: 기존 배포 프로젝트를 재사용하고 새 DB 생성은 중단했다.
- **왜**: 새 조직을 임의로 만들면 계정·비용·데이터 위치가 바뀌기 때문이다.
- **막힌 점 / 바꾼 점**: CLI와 브라우저의 organization이 달라 배포가 거절됐다. 사용자가 선택한
  organization을 다시 확인하고 CLI scope를 맞춘 뒤 같은 build를 재배포했다.
- **배운 것 / 다음**: 여러 계정 환경에서는 프로젝트 생성 전에 CLI와 브라우저 identity를 함께 확인한다.
```
