# 초보 바이브코딩 보호장치

목표: 코드가 빨리 생기는 느낌보다 **기획서대로 작동하는 결과**와 복구 가능한 진행을 우선한다.
이 파일은 기획을 구현 계약으로 바꿀 때와 같은 오류가 반복될 때 읽는다.

## 조사에서 확인된 어려움과 개입

| 어려움 | 관찰 근거 | Orange Build가 할 일 |
|---|---|---|
| 필요한 정보를 빠뜨린 채 표현만 바꿔 다시 요청함 | 초급 학습자 프롬프트 연구에서 성공은 전문용어보다 필요한 정보의 포함 여부와 강하게 연결됐다. | 대상·입력·출력·예외·권한·완료 기준을 구조적으로 추출하고, 구현을 바꾸는 누락만 한 번 묻는다. |
| 첫 화면이나 작동하는 듯한 결과를 완성으로 착각함 | 초보자 연구에서 AI가 잘못된 진척감과 메타인지 문제를 키울 수 있었고 별도 scaffolding이 필요했다. | `SOURCE_PLAN.md`→`REQ-*`→관찰 가능한 증거를 연결하고, 테스트나 실제 결과 없이 PASS라 하지 않는다. |
| AI 결과가 거의 맞지만 디버깅이 더 오래 걸림 | Stack Overflow 2025 조사에서 66%가 거의 맞는 결과, 45.2%가 더 오래 걸리는 디버깅을 문제로 꼽았다. | 같은 오류에 재요청만 반복하지 않고 로그·재현 조건·직전 변경을 읽어 원인 가설 하나와 수정 하나씩 검증한다. |
| 코드가 왜 작동하는지 몰라 복구하지 못함 | 같은 조사에서 20%는 문제 해결 자신감 저하, 16.3%는 코드 이해 어려움을 경험했다. | 각 이정표마다 `무엇을 만들었는지 / 사용자가 확인할 행동 / 아직 안 된 것`을 쉬운 말로 보여준다. |
| 테스트·보안·의존성을 AI에게 다시 맡기고 그대로 믿음 | 생성 코드 보안 연구와 GitHub 지침은 취약 코드, 환각 API·패키지, 약해진 테스트를 별도로 검토하라고 한다. | build·lint·typecheck·test·권한·비밀값·새 의존성을 독립적으로 확인하고 기존 테스트 삭제·약화를 허용하지 않는다. |
| 변경량이 커져 어디서 망가졌는지 모름 | DORA 연구는 AI 도입 효과와 별개로 작은 배치와 강한 테스트가 배포 안정성에 중요하다고 설명한다. | REQ 단위의 작은 변경→검증→경로 지정 commit을 반복하고 마지막 검증 지점을 남긴다. |
| 런타임·CLI·가입·OAuth에서 시작도 못 함 | 초보 설치 연구는 불명확한 절차와 성공 피드백 부족을 주요 마찰로 보고했다. | 기획서에서 준비물을 먼저 뽑고, 설치는 동의 후 대신 실행하며, 가입·본인확인만 사용자에게 요청한다. |

## 실행 보호장치

1. **한 번에 한 완결 흐름**: 입력→처리→검토 가능한 결과가 연결되기 전 다른 기능으로 넓히지 않는다.
2. **작은 검증 루프**: 한 변경마다 가장 가까운 정적 검사·테스트를 실행하고, 실패·누락은 묻지 않고
   자동 수정한 뒤 이정표마다 전체 build와 실제 결과를 다시 확인한다.
3. **증거 우선**: 명령 성공 문구가 아니라 실제 파일, 테스트 결과, dry-run 기록, 배포 URL의 동작을 증거로 쓴다.
4. **두 번 반복되면 진단**: 같은 오류가 두 번 나오면 사용자에게 넘기거나 새 패키지·대규모 재작성을
   시도하기 전에 원인·로그·영향 범위를 다시 진단한다.
5. **초보자용 오류 보고**: `무슨 일 / 가장 가능성 높은 원인 / 지금 할 한 동작 / 데이터·비용 영향` 네 줄로 설명한다.
6. **의존성 검증**: 새 패키지는 공식 registry 존재, 유지 상태, 라이선스, 취약점, 실제 import 필요성을 확인한다.
7. **사람 확인 경계**: 범위 변경·비용·권한 확대·비밀번호·2FA·CAPTCHA·약관·결제·계정 선택·외부
   발송·삭제는 사람이 결정한다. 명백한 버그·테스트 실패·원본 누락 수정은 다시 묻지 않는다.
8. **완료 설명**: 참가자가 직접 확인할 대표 행동 1개를 주고, 남은 항목이 있으면 `N/M 통과`로 말한다.
