# 자가 테스트와 자동 개선 루프

목표: Codex의 GPT-5.6과 각 호스트의 최신 고성능 모델이 가진 계획·도구 사용·검토 능력을 충분히
활용해, 첫 결과를 만든 뒤 AI가 스스로 결함과 누락을 찾고 고쳐 **검증된 결과**로 만든다. 사용자는
명확한 선택과 책임이 필요한 결정에 집중하고, 명백한 버그 수정과 재검증을 대신 지시하지 않는다.

## 1. 모델 사용 원칙

- 교육 환경은 Claude Max 또는 ChatGPT Pro에서 Codex를 쓰는 것처럼 긴 작업과 반복 검증을 감당할
  수 있는 구독 환경을 기본 전제로 한다. Max와 Pro는 모델명이 아니라 사용 환경의 전제다.
- **Codex는 GPT-5.6 선택을 기본 전제**로 하고 `codex-gpt-5p6.md`를 적용한다. Claude Code는 현재
  계정에서 사용할 수 있는 최신 고성능 모델을 사용한다. 두 호스트 모두 계획·코딩·도구 호출·긴
  컨텍스트·검토 능력을 우선한다.
- 모델 변경용 호스트 명령을 실행하거나 모델 설정을 덮어쓰지 않는다. Codex에서 GPT-5.6이 아닌
  모델이 선택된 것이 분명하면 UI에서 GPT-5.6을 선택할 수 있다고 한 번만 안내하고 작업은 계속한다.
  모델 확인 질문을 반복하거나 모델 선택 때문에 구현을 중단하지 않는다.
- 추론 수준을 항상 Max로 강제하지 않는다. 현재 사용자가 선택한 수준을 유지하고, 품질 문제가 생기면
  먼저 요구사항 계약·도구·증거·테스트를 보강한다.
- 플러그인은 산출물·제약·검증 증거·사람 결정 경계를 명확히 하고, 그 안의 조사·구현 순서와 도구
  선택은 모델이 자율적으로 최적화한다.
- 사용량을 아끼기 위해 검증을 생략하거나 원본 범위를 줄이지 않는다. 가까운 검증부터 실행하고,
  이정표에서는 전체 완료 게이트를 실행해 토큰과 시간을 결과 품질에 집중한다.

## 2. 한 슬라이스의 자율 루프

각 REQ·TEST 또는 발견한 결함마다 아래 순서를 완료될 때까지 반복한다.

1. **계약 읽기** — `SOURCE_PLAN.md`의 원문, `PLAN.md`의 REQ·TEST, 현재 결과물 인벤토리를 읽는다.
2. **관찰 기준 정하기** — 사용자가 보게 될 성공·빈 값·오류 결과와 통과 증거를 한 문장으로 적는다.
3. **기준선 만들기** — 가장 가까운 테스트·lint·typecheck·build·fixture·실제 호출을 실행하고
   현재 상태·증거·실패 경계를 남긴다. 가능한 행동은 RED를 먼저 확인한다.
4. **작게 구현하기** — 실패 원인 하나 또는 요구사항 누락 하나를 해결하는 가장 작은 변경을 한다.
5. **가까운 검증 실행** — 바꾼 계층의 테스트와 정적 검사를 즉시 실행한다.
6. **실제 결과 관찰** — 웹앱은 브라우저·console·network·데이터 재조회, AI 스킬은 새 컨텍스트 호출,
   자동화는 fixture·dry-run·run id·결과 재조회로 입력부터 사용자 결과까지 확인한다.
7. **계약 기준 자기 리뷰** — 코드가 의도한 대로가 아니라 원본 기획서가 약속한 대로인지, 빠진 경로·
   상태·오류 처리·권한·보안·불필요한 복잡성이 없는지 비판적으로 다시 본다.
8. **자동 수정과 재검증** — 아래 자동 수정 범위의 문제는 질문하지 않고 고친 뒤 5~7을 반복한다.
9. **이정표 전체 검증** — 가까운 검증이 통과하면 결과물별 전체 test/build/실제 결과 게이트를 다시
   실행한다. 중간 결과를 `PLAN.md`에 전사하지 않고 최종 판정 또는 실제 handoff 때만 한 번 갱신한다.

첫 GREEN이나 HTTP 200에서 끝내지 않는다. 테스트 결과와 사용자가 보는 결과가 모두 계약과 일치해야
`TESTED`다. 수정으로 다른 REQ가 영향을 받을 수 있으면 해당 회귀 검증까지 실행한다.

### 실행 흔적에서 원인 찾기

실패 문구만 보고 코드를 다시 생성하지 않는다. 다음 **trajectory digest**를 짧게 만든다.

```text
입력·상태 → 실행한 행동 → 마지막 정상 경계 → 처음 어긋난 경계 → 실제 출력·로그 → 기대 출력
```

그 뒤 원인을 다음 셋 중 하나로 분류한다.

- `CONTRACT_DEFECT`: REQ·TEST·설계 규칙이 빠졌거나 잘못되어 구현 방향 자체를 보강해야 함
- `EXECUTION_LAPSE`: 올바른 규칙과 코드 경로가 있지만 이번 실행에서 따르지 않았거나 회귀가 생김
- `EXTERNAL_BLOCKER`: 인증·권한·외부 장애·사람 결정 없이는 실행할 수 없음

예시값을 일반 공식으로 만들었거나 확인되지 않은 제품 사실을 화면·출력·자동화에 넣은 경우는 문구
수정만 할 `EXECUTION_LAPSE`가 아니다. `CONTRACT_DEFECT + FACT_UNVERIFIED`로 분류하고
`product-truth-gate.md`의 사람 확인으로 보낸다. 하단 면책 문구를 추가해 통과시키지 않는다.

분류가 불확실하면 가장 싼 판별 검사를 먼저 실행한다. `CONTRACT_DEFECT`는 원본을 바꾸지 않는 범위에서
PLAN의 보조 검증·구현 메모를 보강하고, `EXECUTION_LAPSE`는 코드·설정·실행 순서를 고친다.
`EXTERNAL_BLOCKER`만 사람에게 한 동작을 요청한다.

### 후보 변경 채택 게이트

한 개선 시도에서 원인 1개와 변경 변수 1~2개만 다룬다. 전체 재작성보다 작은 add/delete/replace
patch를 우선하며, `SOURCE_PLAN.md`, 원본 REQ·TEST, 사람의 결정, 보안·승인 경계는 **보호 계약**으로
두어 자동 최적화가 바꾸지 못하게 한다.

후보 변경은 아래가 모두 참일 때만 채택한다.

1. 목표 실패가 기준선보다 관찰 가능하게 좋아졌다. 예: FAIL→TESTED, 오류 재현 해소, 누락 상태 추가.
2. 관련 REQ·TEST와 기존 test/build에서 새 회귀가 없다.
3. 실제 결과 증거가 `TESTED`이며 단순 추론이나 같은 입력을 외운 결과가 아니다.
4. 원본 목적·범위·사람 결정 경계가 보존됐다.

동일하거나 증거가 약한 후보는 채택하지 않는다. 기존 기능이 하나라도 회귀하면 즉시 거절한다.
거절할 때는 이번 시도에서 만든 정확한 변경만 되돌리고 사용자의 기존 변경은 건드리지 않는다.
거절 이유는 다음 시도에서 같은 실패 후보를 반복하지 않도록 짧게 남긴다.

필수 TEST를 숨겨 학습용으로 쓰지 않는다. 대신 최종 후보에는 수정에 직접 사용하지 않은 **인접
검증 1개**를 추가한다. 다른 유효 입력·모바일 상태·재실행·새 컨텍스트처럼 같은 요구사항의 가까운
변형이어야 하며, 이 검증까지 통과해야 후보를 최종 채택한다.

## 3. AI가 묻지 않고 고칠 것

다음은 원본 범위 안의 안전하고 되돌릴 수 있는 수정이므로 자동으로 처리한다.

- failing test, lint·type 오류, production build 오류와 명백한 회귀
- REQ·TEST에 적힌 기능, 경로, 파일, 트리거, 출력, 로딩·빈 값·오류·성공 상태의 누락
- 실제 console 오류, 실패한 network 요청, 잘못된 데이터 매핑, 저장 후 재조회 불일치
- 깨진 링크·버튼·validation, 모바일 overflow, 기본 접근성 이름·키보드 동작 누락
- 스킬의 잘못된 trigger·비트리거 개입·깨진 fixture·도구 없음 폴백
- 자동화의 중복 생성·무한 재시도·불충분한 로그·dry-run과 live 경로 불일치
- 기존 동작을 바꾸지 않는 단순화, 중복 제거, 최소한의 테스트와 문서 보강

이 문제를 발견했다고 사용자에게 `고칠까요?`라고 묻지 않는다. 고치고 같은 입력으로 재현해 테스트·
CI·배포 로그로 증명한다. 수정 목록을 매번 설명하지 않으며, P0/P1을 고쳤거나 사용자가 요청한
경우에만 최종 보고에 대표 항목을 짧게 남긴다.

## 4. 사람이 결정할 것

다음은 여러 정답이 있거나 책임·비용·권한이 달라지므로 변경 전에 사람의 명시적 결정을 받는다.

- 원본 범위 추가·삭제, 핵심 사용자·업무 흐름·성공 기준 변경, 서로 충돌하는 제품 선택
- 출처가 불명확한 금액·비율·정량 효과·자격·정책·개인정보·외부 실행 규칙의 실제 값
- 브랜드·표현·시각 취향처럼 기획서에 답이 없고 결과 방향을 크게 바꾸는 선택
- 유료 요금제·과금 자원·구매·결제 또는 예상 비용 증가
- 새 개인정보 수집, 공개 범위 변경, 권한·OAuth scope 확대, 보안 경계 완화
- 데이터 삭제·덮어쓰기·마이그레이션·복구하기 어려운 외부 변경
- 이메일·메시지 발송, 공개 게시, live 자동화 활성화처럼 타인이나 외부 시스템에 영향을 주는 행동
- 여러 계정·team·organization·production 대상 중 어느 것을 사용할지 선택
- 테스트를 삭제·약화하거나 REQ를 미완료로 남기고 릴리스할지 결정

질문할 때는 `결정할 것 / 권장안과 이유 / 다른 선택의 영향 / 지금 필요한 한 답`만 보여준다. 불확실한
제품 사실은 `product-truth-gate.md`의 형식으로 최적의 권장안을 먼저 제시한다. 이미
기획서나 대화에서 결정한 내용은 다시 묻지 않는다. 사람이 결정하기 전에도 로컬 구현·dry-run·
읽기 전용 검증처럼 되돌릴 수 있는 작업은 계속한다.

## 5. 반복 실패와 막힘

- 같은 오류가 두 번 나오면 새 코드를 더 생성하지 말고 **DIAGNOSE**로 전환한다. 전체 로그, 재현
  조건, 직전 변경, 환경 차이, 데이터 흐름을 읽고 경쟁 가설을 세운 뒤 가장 싼 판별 검사를 한다.
- 진단 뒤 원인이 좁혀지면 수정 하나만 적용하고 같은 재현으로 다시 검증한다. 사용자에게 디버깅을
  떠넘기거나 막연히 `다시 시도해 보세요`라고 하지 않는다.
- 여러 증거 기반 시도에도 진전이 없으면 마지막 성공 지점, 실행한 검사, 남은 가설을 기록한다.
  계정 인증·외부 장애·사람 결정처럼 AI가 해결할 수 없는 실제 blocker가 확인된 때만 사용자가 할
  한 동작을 요청한다. 단순히 세 번 실패했다는 이유만으로 질문하지 않는다.
- 우회가 원본 범위·비용·권한·데이터를 바꾸면 자동 적용하지 않고 사람 결정 게이트로 보낸다.

반복 실패에서 얻은 중간 교훈은 사용자가 과정 기록을 요청한 경우에만 `MEMORY.md`에 남긴다. 다만
최종 완료 판정에서는 요청 여부와 무관하게 `memory-log.md`의 최종 검증 블록 하나를 기록한다. 세션
기록이나 모델의 자기평가만으로 플러그인·스킬 지침을 자동 수정하지 않는다. 재사용할 규칙 후보는
실제 여러 사례와 별도 fixture에서 기준선보다 좋아진 뒤 사람이 검토할 수 있는 diff로 제안한다.

## 6. 결과물별 실제 관찰

| 결과물 | 자동 개선에 쓰는 실제 증거 |
|---|---|
| `web_app` | production URL의 핵심 흐름, console·network, 저장 후 재조회, 역할·모바일·오류 상태 |
| `ai_skill` | 구조 validator, 긍정/비트리거 fixture, 도구 없음, 이름·경로·정답을 숨긴 새 컨텍스트 호출 |
| `automation` | 단위 fixture, dry-run, 같은 입력 2회, 제한 재시도, 승인된 live sample과 결과 재조회 |

새 컨텍스트 실제 호출이 결과물 계약에 있으면 구현자의 경로·정답 힌트를 넘기지 않고 실행한다. 별도
독립 reviewer는 반복 회귀, 고위험 외부 변경, 상충하는 증거, 모호한 품질, 두 버전 비교가 있을 때만
`SOURCE_PLAN.md`, `PLAN.md`, 결과물, 증거를 주어 활성화한다. 그 외에는 구현 검증과 분리된
self-review를 한 번 수행하고 `independent_review: NOT_NEEDED`와 이유를 남긴다. P0/P1은 자동 수정 뒤
전체 검증을 다시 실행한다. P2/P3도 원본 범위 안의 안전한 수정이면 고치며, 제품 선택이나 위험
변경일 때만 사람에게 결정권을 돌린다.

## 7. 완료 보고

최종 보고는 결과를 먼저 보여주고 아래 필수 정보만 남긴다.

- 실제로 실행해 통과한 REQ·TEST와 대표 증거
- 아직 `TESTED`가 아닌 항목과 실제 blocker

AI가 테스트·리뷰에서 발견해 자동으로 고친 항목, 채택·거절 후보 수, 사람이 결정한 상세 내역은
P0/P1·중요 범위 변경이 있었거나 사용자가 요청했을 때만 덧붙인다.

사용자에게 직접 확인할 대표 행동 하나를 주되, 그 확인을 플러그인의 테스트 대신으로 사용하지 않는다.

## 참고한 방법

- [Hermes Agent Self-Evolution](https://github.com/NousResearch/hermes-agent-self-evolution) — 실행 흔적
  기반 반성, 원래 의미 보존, 전체 테스트·회귀 게이트, 사람 검토
- [Microsoft SkillOpt](https://github.com/microsoft/SkillOpt) — 제한된 텍스트 patch, 기준선 비교,
  validation-gated accept/reject, 거절 기록과 인접 평가

두 프로젝트의 최적화 프레임워크나 모델 설정을 설치·복제하지 않는다. Orange Build에는 결과물 한
건을 안전하게 개선하는 절차만 호스트 중립 규칙으로 적용한다.
