# AI 작업 스킬 구현

목표: `PLAN.md`의 반복 작업을 Codex와 Claude Code가 모두 읽을 수 있는 작고 검증 가능한 스킬로
만든다. 설명문만 작성하고 끝내지 않고, 실제 예시 입력으로 호출 결과까지 확인한다.

`delivery_intent`가 `implement_and_release`면 실제 호출 확인에서 멈추지 않는다. 정확한 파일을
commit·push하고, 기획서에 marketplace·설치 대상이 있으면 그 대상에서 새 컨텍스트 호출까지
확인해야 완료다.

시작할 때 `verification-loop.md`를 읽는다. `PLAN.md`의 TEST↔REQ 연결과 결과물 인벤토리를
구현 순서와 완료 증거의 기준으로 삼는다.

## 1. 스킬 계약 확정

구현 전에 `PLAN.md`의 유형별 설계에 다음이 있는지 확인한다.

- 짧은 hyphen-case 이름
- 긍정 트리거 3개: 사용자가 실제로 말할 법한 표현
- 비트리거 2개: 비슷하지만 이 스킬이 끼어들면 안 되는 요청
- 필수·선택 입력과 빈 입력 처리
- 바로 사용할 수 있는 출력 형식
- 정상·오류·도구 없음 시 실행 흐름
- 개인정보·외부 변경·사용자 승인 경계
- 검증 fixture

빠진 항목은 원본에서 추론해 `가정`으로 적는다. 결과를 크게 바꾸는 내용만 묻는다.

구현 전에 결과물 인벤토리에서 필수 `SKILL.md`, script/reference/asset, 약속한 출력, fixture의
예상 목록과 수량을 다시 센다. 연결된 TEST의 `준비`, `행동`, `기대 결과`, `통과 증거`가 어느
파일과 실제 호출로 증명되는지 표시한다.

## 2. 가장 작은 구조 만들기

한 스킬 저장소라면 루트에 `SKILL.md`를 둔다. 여러 스킬을 담는 플러그인이라면
`skills/<skill-name>/SKILL.md`를 쓴다. 이름과 폴더명을 일치시킨다.

```text
<skill-name>/
├── SKILL.md
├── agents/openai.yaml   # 생성 도구가 있을 때 권장
├── scripts/             # 반복되거나 결정적 실행이 필요할 때만
├── references/          # 긴 규칙·스키마가 필요할 때만
└── assets/              # 결과에 복사할 템플릿이 있을 때만
```

README·변경기록·설치 가이드처럼 스킬 실행에 불필요한 파일을 스킬 폴더 안에 만들지 않는다.
프로젝트 저장소 자체의 README가 필요하면 스킬 폴더 밖 루트에 둔다.

사용 가능한 `skill-creator` 또는 동등한 scaffold 도구가 있으면 그 구조와 validator를 재사용한다.
없으면 위 최소 구조를 직접 만든다.

## 3. 구현 순서

1. 각 TEST와 REQ에서 자동화할 수 있는 가장 작은 행동을 fixture나 구조 검증으로 먼저 표현하고,
   의도한 이유로 실패하는 **RED**를 확인한다.
2. 반복 계산·파일 변환·정형 검증이 있으면 `scripts/`부터 최소 구현해 **GREEN**으로 만든다.
   스크립트는 명시적 인자를 받고, 비밀값을 출력하지 않으며, 실패 시 non-zero로 끝나게 한다.
3. 긴 도메인 규칙이나 스키마는 `references/`로 옮긴다. `SKILL.md`에서 **언제 읽을지** 한 단계
   깊이로 연결한다.
4. 출력에 쓰는 고정 템플릿만 `assets/`에 둔다.
5. 마지막에 `SKILL.md`를 작성하고, 동작을 유지한 채 중복·불필요한 파일·과도한 지침을 줄이는
   **REFACTOR** 뒤 같은 검증을 다시 실행한다.

`SKILL.md` frontmatter는 호환성을 위해 `name`, `description`만 둔다. description에는 무엇을 하는지와
언제 호출할지를 함께 쓰고, 긍정 트리거의 범위를 포괄하되 비트리거까지 잡아먹지 않게 한다.
본문은 명령형으로 쓰고 핵심 실행 순서·분기·완료 조건만 둔다. 500줄을 넘기지 않는다.

호스트별 표기는 지침 안에서 필요할 때만 분기한다.

- Codex: 자연어 또는 `$skill-name`
- Claude Code: 자연어 또는 `/skill-name`

둘 중 하나의 명령 표기만을 유일한 호출법으로 가정하지 않는다.

## 4. 스크립트와 구조 검증

- 추가한 스크립트는 정상 fixture와 빈/잘못된 입력 fixture로 직접 실행한다.
- 사용할 수 있는 공식 `quick_validate.py`가 있으면 스킬 폴더에 실행한다.
- 없으면 최소한 다음을 확인한다: YAML frontmatter 파싱, 필수 필드, 폴더명=이름, 참조 파일 존재,
  placeholder·TODO 없음.
- `agents/openai.yaml`을 만들었다면 SKILL.md의 이름·설명·기본 프롬프트와 일치하는지 확인한다.

검증 명령과 실제 출력을 `PLAN.md`의 검증 증거 표에 남긴다.
명령 성공, 구조만 읽은 판단, 실제 호출을 구분해 `TESTED | PARTIAL | INFERRED` 등급도 적는다.

## 5. 실제 호출 포워드 테스트

먼저 source 스킬 경로를 명시해 정상 실행 자체를 확인한다. 그다음 격리된 테스트 설치나 실제
discovery 경로에서 **새 컨텍스트**를 열고, 스킬 이름·경로·예상 답을 알려주지 않은 사용자 요청으로
자동 선택 여부를 확인한다. 비트리거도 같은 조건에서 테스트한다.

최소 시나리오:

1. 긍정 트리거 3개 — 모두 스킬을 사용하고 약속한 출력이 나오는지
2. 비트리거 2개 — 스킬이 부적절하게 개입하지 않는지
3. 정상 fixture — 핵심 결과가 맞는지
4. 빈/깨진 입력 — 조용히 실패하거나 꾸며내지 않고 다음 행동을 알려주는지
5. 외부 도구 없음 — 안전한 폴백 또는 명확한 blocker를 주는지

실패하면 description·분기·스크립트를 고치고 같은 시나리오를 다시 실행한다. 단순히 한 번 좋은
출력이 나온 것으로 끝내지 않는다. 대표 입력의 사용자 요청 → 스킬 자동 선택 → 입력 해석 →
script/reference 사용 → 약속한 최종 출력 경계를 새 컨텍스트에서 끝까지 관찰해야 `TESTED`다.
source 경로를 알려준 실행만 통과하거나 일부 출력만 맞으면 `PARTIAL`, 파일을 읽고 동작을 예상했으면
`INFERRED`이며 TEST PASS가 아니다.

포워드 테스트 뒤 결과물 인벤토리의 예상 파일·출력·fixture 수량과 실제 수량을 대조한다. 점검 범위는
REQ와 연결된 예상 결과물 경로로 제한하고, 그 안의 placeholder, 빈 script, 고정 성공 출력, no-op을
찾는다. 저장소의 무관한 예시·TODO를 이번 결과물 blocker로 확대하지 않는다.

## 6. 첫 작동 결과와 저장

가장 대표적인 긍정 요청 하나를 실제로 실행해 결과를 사용자에게 보여준다. 이것이 스킬 유형의
`첫 작동 결과`다. `PLAN.md`에서 관련 REQ의 구현 위치·검증·상태를 갱신하고 진행 상황의
`첫 작동 결과`를 체크한다.

코드·fixture·검증 증거·체크 상태를 한 커밋에 담는다.
이번 스킬 구현에서 바꾼 정확한 경로만 `git add --`로 stage하고 cached 목록을 확인한다.

```bash
git commit -m "구현: AI 작업 스킬"
git push
```

로컬 설치가 검증에 필요하면 source를 복사해 드리프트시키지 말고, 가능한 install/symlink 방식이나
새 컨텍스트에서 source 경로를 직접 지정한다. 설치 복사본을 만들었다면 source와 파일 checksum을
비교한다.

모든 REQ 구현이 끝나면 `전체 요구사항 구현`을 체크하고 `phase-verify.md`로 이어간다.
